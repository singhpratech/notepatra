# Notepatra v0.1.34 — Fold-margin Dark-theme fix + structural test

**Released:** 2026-04-26

User reported via Windows screenshot of the SQL Formatter panel: a stark **white vertical strip** between the line numbers and the SQL content on Dark theme. The user circled it in red and asked us to do "very deep theme-level testing" so this class of bug doesn't keep slipping through.

---

## 1. The bug

QScintilla's `setFolding(BoxedTreeFoldStyle, 2)` enables code folding by adding a fold-marker margin at slot 2. But `setFolding()` does NOT theme the margin's background — that's a separate call: `setFoldMarginColors(QColor fore, QColor back)`. Without that call, QScintilla paints the fold margin in **default white**.

Affected widgets:

| File | Has `setFolding`? | Style | `setFoldMarginColors`? | Visible bug |
|---|---|---|---|---|
| `src/editor.cpp` | yes | BoxedTree | ✓ themed | clean |
| `src/compare.cpp` | yes | NoFoldStyle | n/a | clean (no margin) |
| `src/sqlfmtpanel.cpp` | yes | BoxedTree | ✗ MISSING | white strip on Dark |
| `src/fmtpanel.cpp` (JSON / HTML / Bracket Tools) | yes | BoxedTree | ✗ MISSING | white strip on Dark |

The main editor was correct because `editor.cpp` had been wired with all margin colours during earlier theme work. The four formatter panels were copy-pasted from a template that pre-dated the Dark theme.

---

## 2. The fix

Three call additions across two files:

### `src/sqlfmtpanel.cpp` — was missing all margin colours

Pre-v0.1.34 the SQL Formatter set ONLY caret + paper + text colour:

```cpp
// before
m_output->setCaretLineBackgroundColor(...);
m_output->setCaretForegroundColor(...);
m_output->setPaper(...);
m_output->setColor(...);
```

Post-v0.1.34:

```cpp
// after
m_output->setCaretLineBackgroundColor(...);
m_output->setCaretForegroundColor(...);
m_output->setPaper(...);
m_output->setColor(...);
m_output->setMarginsBackgroundColor(QColor(pal.bg));
m_output->setMarginsForegroundColor(QColor(pal.textMuted));
m_output->setFoldMarginColors(QColor(pal.bg), QColor(pal.bg));
```

### `src/fmtpanel.cpp` — had margin BG/FG but not fold margin

Already set `setMarginsBackgroundColor` + `setMarginsForegroundColor`. Added `setFoldMarginColors(fp.editorBg, fp.editorBg)` in BOTH:
- The constructor (initial setup)
- The `onThemeChanged()` reapply path (so Dark↔Light switch picks it up)

## 3. Structural test — v0.1.34's anti-regression net

Scintilla's `SCI_*` API doesn't include `SCI_GETFOLDMARGINCOLOUR` — only the `SET` command exists. So we can't round-trip the colour at runtime to verify the call happened. Instead `test_palette.cpp` now does a **structural source check**:

For each editor-hosting `.cpp` file (`sqlfmtpanel.cpp`, `fmtpanel.cpp`, `compare.cpp`, `editor.cpp`), the test:

1. Reads the file as text at test time
2. Looks for `setFolding(`
3. Looks for `NoFoldStyle` (escape hatch — files using NoFoldStyle have no fold margin so theming is moot)
4. Looks for `setFoldMarginColors(`
5. **Pass condition**: file either doesn't call `setFolding`, OR calls it only with `NoFoldStyle`, OR calls both `setFolding` AND `setFoldMarginColors`
6. **Fail condition**: file calls `setFolding(...)` with a real fold style but does NOT call `setFoldMarginColors`

Running the test:

```
ok   FoldMargin sqlfmtpanel.cpp    (folding=yes, colors=yes)
ok   FoldMargin fmtpanel.cpp       (folding=yes, colors=yes)
ok   FoldMargin compare.cpp        (folding=none, colors=n/a)
ok   FoldMargin editor.cpp         (folding=yes, colors=yes)
```

If anyone adds a 5th editor panel and forgets `setFoldMarginColors`, CI fails. If anyone removes `setFoldMarginColors` from an existing file, CI fails.

Why structural instead of runtime: Scintilla doesn't expose the get-side of fold-margin colour, the panels need full `Config::instance()` + theme palette + lexer setup to instantiate, and the bug class is simply "did you make this call?" — exactly what a textual check answers. Faster + simpler + same coverage.
