# Notepatra v0.1.35 — Coding Mode is now AGENTIC

**Released:** 2026-04-26

The AI can now read files and list directories on its own.

Toggle Coding Mode, ask it about your code, and it'll go read what it needs. Works with **every backend** Notepatra supports — Ollama (local), llama.cpp (local), and any OpenAI-compatible service (OpenRouter, OpenAI, Anthropic via proxy, vLLM, LM Studio, Gemini via OpenRouter).

## What changed

When Coding Mode is on:

```
You: refactor the auth middleware to use the new logger

🔧 list_dir (.) → 12 entries
🔧 read_file (src/middleware.rs) → 247 lines
🔧 read_file (src/logger.rs) → 89 lines

QWEN3:14B
⏱ 1248 tok · 18.4 tok/s · 67.8 s
Looking at the existing auth middleware, here's the refactored version that
uses the new structured logger... (continues with concrete code based on
what was actually in the files)
```

That's not pre-canned text. The model called `list_dir(".")` to see what's in your project, then `read_file("src/middleware.rs")` to read the auth code, then `read_file("src/logger.rs")` to understand the new logger interface, and only THEN wrote the refactor. Every read shows up as an inline `🔧` card so you see exactly what it touched.

## How it works

### Backend coverage

| Backend | Endpoint | Model examples |
|---|---|---|
| **Ollama** (local) | `/api/chat` with `tools` array | qwen3, llama3.1+, hermes3, mistral-nemo, command-r-plus, granite3, gpt-oss, deepseek-v3/r1 |
| **llama.cpp** (local) | `/v1/chat/completions` (needs `--jinja`) | any model with native template tool support |
| **OpenAI-compat** | `/v1/chat/completions` | OpenRouter (any tool-trained model behind it), OpenAI direct, LM Studio, vLLM, Jan, Anthropic-via-proxy, Gemini-via-OpenRouter |

The wire-format research (multi-agent, Apr 2026) verified:
- Ollama emits **atomic** tool_calls in NDJSON chunks, with `arguments` as a parsed JSON object (not string), and no `id` — Notepatra synthesizes one client-side.
- OpenAI-compat emits **streamed** tool_calls in SSE deltas, with `arguments` arriving as fragments accumulated per `index` until `finish_reason: tool_calls`, with backend-supplied `id`s.

The parser handles both formats; same agent loop runs on top.

### The two tools

#### `read_file(path, offset?, limit?)`

Reads a workspace file. Returns `cat -n` line-numbered content.

- **Default:** 1500 lines, 2000-character per-line truncation.
- **Pagination:** model can pass `offset`+`limit` for chunked reads of large files.
- **Binary detection:** NUL byte in the first 8 KB → `error_kind: binary`, no base64 fallback.
- **Truncation marker:** if `total_lines > offset + limit`, returns `truncated: true` so the model knows to follow up.

#### `list_dir(path)`

Lists one level of entries. Returns `[{name, type: "file"|"dir", size?}, ...]`.

- **Depth:** 1 (no recursion). For recursion the model uses follow-up calls.
- **Hidden files:** included (`.env`, `.github`, `.vscode` are real files developers want to see).
- **Junk filtered:** `.git`, `node_modules`, `build`, `target`, `dist`, `.venv`, `venv`, `__pycache__`, `.cache`, `.gradle`, `DerivedData`, `.idea`, `.vs` skipped at the entry level.
- **Cap:** 500 entries; if exceeded, returns `truncated: true` with total count.

## Security model — three layers, defense in depth

### Layer 1 — Workspace anchor

Every tool path is canonicalized via `QFileInfo::canonicalFilePath()` (which **resolves symlinks**). The result must equal the workspace root OR start with `canonical(workspaceRoot) + "/"`. Otherwise → `error_kind: outside_workspace`.

```
workspace = /home/u/myproj
read_file("../../etc/passwd") → canonicalizes to "/etc/passwd" → REJECTED
read_file("/etc/passwd")      → REJECTED (not under workspace)
read_file("src/main.rs")      → canonicalizes to "/home/u/myproj/src/main.rs" → OK
```

### Layer 2 — Hardcoded deny-list

Even paths INSIDE the workspace are refused if they match secret patterns. Catches the symlink-to-secret case where the workspace contains a link pointing at `~/.ssh/id_rsa`. The deny-list lives in code, not user settings, so the user can't accidentally widen it:

```
~/.ssh/      ~/.gnupg/    ~/.aws/      ~/.netrc       ~/.npmrc
~/.pypirc    ~/.docker/config.json     /etc/passwd    /etc/shadow
*.pem        *.key        *.pfx        *.p12
id_rsa*      id_ed25519*  id_ecdsa*    id_dsa*
authorized_keys           known_hosts
```

### Layer 3 — Structured errors

Every tool returns:

```json
{"ok": true,  "result": {...}}
or
{"ok": false, "error_kind": "not_found|denied|too_large|outside_workspace|binary|io_error",
              "message": "...", "path": "..."}
```

Errors come back as data the model can recover from (try a different path, summarise what it has, give up cleanly), not as exceptions that crash the conversation. `error_kind: denied` deliberately doesn't echo the file's contents in the error message — but does tell the model the rule fired so it doesn't loop trying.

## Tool-call budget

Hard cap **25 tool calls per user turn** (matches Cursor / Aider). When exhausted, the model receives a structured error: *"Tool-call budget exhausted (25 calls this turn). Stop and summarise what you've found."* Prevents runaway loops on confused models.

---

## Anti-tool-call layer becomes conditional

Pre-v0.1.35 every chat request carried an "anti-tool-call layer" in the system prompt — *"you have no tools, do not produce JSON tool calls"* — to suppress the qwen3.5/hermes/llama-3.1+ default agent-output behaviour. That layer is now **conditional**: when tools ARE attached, it's replaced with a brief tool-mode preamble telling the model the tools are available and to use the structured `tool_calls` field. Telling the model both "no tools exist" AND attaching tool definitions in the same request was producing contradictory guidance.

---

## Temperature pinned to 0.1 for tool-bearing requests

Per Ollama / multi-editor research: high temperature produces malformed JSON in `arguments` even on tool-trained models. 0.1 is the documented sweet spot for reliable tool-call argument parsing.

## Try it

After upgrading:

1. Open a folder as workspace (`File → Open Folder`)
2. Pull a tool-capable model: `ollama pull qwen3:14b` (or use any of the listed cloud models via OpenAI-compat URL)
3. Toggle **Coding Mode** in the AI panel
4. Ask it about your code: *"What does the auth flow look like?"* / *"Refactor the logger to use structured fields"*
5. Watch the inline `🔧 read_file (...)` cards as the model walks your workspace and responds with grounded, file-accurate answers

If the model isn't in the tool-allowlist, you'll just get the existing v0.1.34 behaviour (no tools sent, normal chat). The Coding Mode toggle is still useful for code-only output.
