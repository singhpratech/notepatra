# Notepatra v0.1.33 — Linux emoji fix + comprehensive palette test coverage

**Released:** 2026-04-26

User reported `Hello! 👋` from an AI response rendering as `Hello! □` on Linux but fine on Windows. Root cause + fix + (more importantly) test coverage so the regression can't come back. Same testing pass surfaced two more latent palette bugs (Python built-ins + SQL user-defined slots) which got fixed in the same release.

---

## 1. Linux emoji rendering — `Hello! 👋` → `Hello! □`

### The bug

A user shared an AI response screenshot from Linux:

```
QWEN3.5:9B
⏱ 48 tok · 3.4 tok/s · 14.1 s
Hello! □ I'm your AI coding assistant. ...
```

The `👋` (U+1F44B, waving hand) showed as `□` tofu. On Windows the same response rendered correctly with the emoji intact.

### Root cause

Linux's text fonts (Inter, Noto Sans, DejaVu Sans, Cantarell, Ubuntu, etc.) don't ship emoji glyphs. Qt's HarfBuzz text shaper falls back to whatever fonts are listed in the CSS `font-family` chain — and Notepatra's `notepatraUiCssFamily()` in `src/fonts.h` only listed text fonts:

```cpp
// before v0.1.33
return "\"Inter\", \"Segoe UI\", \"SF Pro Text\", \"Noto Sans\", \"Cantarell\", "
       "\"Ubuntu\", \"DejaVu Sans\", sans-serif";
```

When the shaper encountered `U+1F44B`, none of those fonts had a glyph → tofu fallback character.

Why Windows worked: "Segoe UI" auto-pairs with "Segoe UI Emoji" at the OS level — Windows fills the gap silently.

### The fix

Both CSS family resolvers (`notepatraUiCssFamily()`, `notepatraCodeCssFamily()`) now end with an emoji fallback chain:

```cpp
#define NOTEPATRA_EMOJI_FALLBACK \
    "\"Apple Color Emoji\", \"Segoe UI Emoji\", \"Noto Color Emoji\", " \
    "\"Twemoji Mozilla\", \"Twitter Color Emoji\", \"Symbola\""

inline QString notepatraUiCssFamily() {
    return "\"Inter\", \"Segoe UI\", ..., \"DejaVu Sans\", "
           NOTEPATRA_EMOJI_FALLBACK ", sans-serif";
}
```

Order matters: text fonts FIRST so Latin / CJK / etc. shape correctly, then emoji fonts so the shaper only consults them for codepoints the primary fonts lack. macOS → Windows → Linux/Android color → Twemoji 3rd-party → Symbola monochrome fallback.

### Qt5 caveat

Qt5's color emoji rendering on Linux is sometimes monochrome (the CBDT/CBLC color table in Noto Color Emoji isn't always picked up). If `👋` shows as a black silhouette instead of yellow, that's a Qt5 limitation, not a Notepatra bug. Workarounds: install Twemoji Mozilla (uses SVG-in-OpenType which Qt5 handles better), or install a Symbola variant. Qt6 fully supports color emoji.

## 2. Test coverage — "how come we're missing this?"

### What got added

`test_palette.cpp` was 38 colour checks before; now 56. New assertions cover every per-language brand palette added in v0.1.32:

**PowerShell ISE signature** (the user's actual `New-Object` complaint from v0.1.31):
- style 5 (variable, `$var`) → `#FF4500` OrangeRed (ISE)
- style 9 (cmdlet, `New-Object`) → `#0000FF` pure blue (ISE)
- style 10 (alias, `ls` / `gci`) → `#0080FF` lighter cyan

**Python brand** (VS Code Dark+ canonical):
- style 8 (class name) → amber `#795E26`
- style 9 (function name) → amber `#795E26`
- style 14 (highlighted identifier / built-in) → teal `#267F99`

**SQL brand** (SSMS canonical):
- style 19 (user-defined keyword 1, where `INT`/`VARCHAR`/`COUNT` go) → magenta `#FF00FF`

**JavaScript brand**:
- style 16 (secondary keyword) → teal `#267F99`

**Font fallback chain** — 6 assertions verifying `Apple Color Emoji`, `Segoe UI Emoji`, `Noto Color Emoji` all appear in BOTH `notepatraUiCssFamily()` AND `notepatraCodeCssFamily()`. If anyone ever removes them, the test fails before regression hits users.

### Two more bugs caught by the new tests

The test expansion immediately surfaced TWO bugs in v0.1.32's brand palette work — neither shipped with the v0.1.32 binaries because the assertions failed during the v0.1.33 test pass:

**Python built-ins painted as default text** (not the claimed teal). Why: `QsciLexerPython` style 14 description is `"Highlighted identifier"`. The substring `identifier` hit `npp_palette.cpp`'s catch-all identifier matcher BEFORE any keyword matcher could see it. So the per-language `npKeyword2` brand colour for Python (set to teal in the Python branch) never reached style 14. Built-ins like `print`, `len`, `range` rendered black on light theme.

**SQL user-defined keywords painted as default text** (not the SSMS magenta). Why: `QsciLexerSQL` exposes "User defined 1" at style 19 (description literal: `User defined 1`). That string doesn't contain `keyword` — so the keyword sub-branch logic in the matcher chain never hit it. Style 19 fell through to default text instead of SSMS magenta.

Both fixed by extending the `npp_palette.cpp` matcher chain with a single new branch BEFORE the generic `identifier` matcher:

```cpp
else if (d.contains("highlighted") ||
         d.contains("user defined") || d.contains("user-defined")) {
    fg = npKeyword2;
    lexer->setFont(bold, i);
}
```

This single branch fixes both the Python and the SQL cases. Verified by the new test assertions.

### What this catches going forward

If anyone:
- Removes an emoji font from the CSS chain → font-fallback test fails
- Changes Python's class-name colour from amber → Python test fails
- Reverts SQL's magenta brand → SQL test fails
- Removes the PowerShell `$variable` red → PowerShell test fails
- Refactors the matcher chain and breaks identifier-vs-highlighted ordering → Python built-in test fails

Regressions die at CI, not at user screenshots.

## 6. Try it

After upgrading on Linux:

1. Ask the AI a casual question — `Hello!`, `Hi there!`. Most local models reply with an emoji greeting (`👋`, `🙂`, etc.). With v0.1.33 the emoji renders as a glyph instead of `□` tofu.
2. Open a Python file with `print(x)` or `len(items)` — `print` and `len` paint teal `#267F99`, distinct from blue keywords. Was rendering black on light theme in v0.1.32.
3. Populate SQL keyword set 2 (any future feature that adds INT/VARCHAR to it) — those tokens paint magenta `#FF00FF`. Was rendering black in v0.1.32.
4. Open a `.ps1` with `$var` — paints OrangeRed `#FF4500`. With `Get-Item` / `New-Object` — paints blue `#0000FF`. Already worked in v0.1.32; now CI-verified.
