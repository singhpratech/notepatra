# Notepatra v0.1.74 — MSI upgrade fix for `notepatra-local-ai`

Released: 2026-05-11

Targeted patch on top of v0.1.73. Two focused changes:

1. **Windows MSI** — `notepatra-local-ai` no longer drops into the
   Repair / Remove maintenance UI when upgrading from v0.1.72 / v0.1.73.
2. **Website** — `docs/index.html` shows only the latest release
   card. Every older release lives entirely on GitHub; the slim
   "horizontal lines" of older versions are gone.

No editor, AI dock, or core-feature changes.

---

## 1. MSI upgrade bug — `notepatra-local-ai`

### The bug

> "MSI update is not happening properly for notepatra-local-ai —
> it's going to Repair and Remove."
> "The regular MSI is perfect, please fix."

When a user had **both** the regular Notepatra MSI and the cloud-free
`notepatra-local-ai` MSI installed side-by-side (as the v0.1.72
"parallel install" model explicitly supports), upgrading the local-ai
MSI from v0.1.72 → v0.1.73 dropped into Windows Installer's
maintenance UI ("Repair / Remove") instead of running a clean major
upgrade.

The regular MSI was unaffected because most users only ever install
that one flavor.

### Root cause

All three `<Component>` elements in `installers/windows.wxs` used
**hardcoded Component GUIDs**:

```xml
<Component Id="MainExecutable"      Guid="A2F3B641-8E7D-4C5A-…"  …>
<Component Id="ApplicationShortcut" Guid="C3D4E5F6-7A8B-9C0D-…" …>
<Component Id="DesktopShortcut"     Guid="D4E5F6A7-8B9C-0D1E-…" …>
```

These GUIDs were shared between the regular and local-ai flavors of
the MSI. Windows Installer treats a Component GUID as a system-wide
unique identifier — when two products register the same Component
GUID, Windows reference-counts them as the **same component** even
though they install to different paths (`C:\Program Files\Notepatra\`
vs `C:\Program Files\Notepatra Local AI\`).

When the user had both flavors installed and ran the local-ai
upgrade MSI:

- Windows saw the shared components already registered (refcount = 2)
- The MajorUpgrade tried to uninstall v0.1.72 components but Windows
  refused to fully release them (still referenced by regular)
- The install transitioned into "maintenance mode" instead of the
  upgrade flow, presenting Repair / Remove

Diagnosed by extracting `ProductCode` / `UpgradeCode` / `ProductVersion`
from both MSIs (`strings -e s notepatra-local-ai-0.1.7?.msi`) and
confirming all three Component GUIDs appeared identically in regular
`v0.1.73` *and* local-ai `v0.1.72` *and* local-ai `v0.1.73`.

### Fix

Switched all three Component declarations to `Guid="*"`:

```xml
<Component Id="MainExecutable"      Guid="*" Win64="yes" …>
<Component Id="ApplicationShortcut" Guid="*" …>
<Component Id="DesktopShortcut"     Guid="*" …>
```

`Guid="*"` makes WiX auto-generate the component GUID **deterministically
from the component's KeyPath**. The KeyPath includes `INSTALLFOLDER`,
which differs between the two flavors:

- Regular: `INSTALLFOLDER = "Notepatra"`
- Local-AI: `INSTALLFOLDER = "Notepatra Local AI"`

→ Different KeyPath → Different auto-generated Component GUID → Windows
treats them as genuinely separate components and the refcount conflict
disappears.

Also added `AllowSameVersionUpgrades="yes"` to the `<MajorUpgrade>`
element so re-running the same-version MSI goes through the install
flow instead of the maintenance UI.

### How the fix migrates existing installs

For users on local-ai v0.1.72 or v0.1.73, the v0.1.74 MSI flow is:

1. v0.1.74 MSI runs, MajorUpgrade detects the installed UpgradeCode
   `{B7C8D9E0-1F2A-3B4C-5D6E-7F8A9B0C1D2E}` (unchanged)
2. Older version is uninstalled, releasing its shared-GUID components
   (regular install's refcount on those components drops by 1)
3. v0.1.74 installs with new auto-generated GUIDs that **do not
   collide** with regular's GUIDs
4. From v0.1.74 onward the two flavors are fully independent in
   Windows Installer's database

If an affected user is stuck in the maintenance UI, they can manually
uninstall the broken v0.1.72/v0.1.73 local-ai via Add/Remove Programs
first, then install v0.1.74 cleanly — but normal MajorUpgrade should
just work.

### Files changed

- `installers/windows.wxs` — three `Guid="*"` substitutions +
  `AllowSameVersionUpgrades="yes"` on `<MajorUpgrade>`. 22-line diff.

## 2. Website — older release rows removed

### The change

`docs/index.html` previously demoted older releases to slim
horizontal "version-card-link" rows (one per release, linking back to
GitHub). v0.1.74 strips them entirely. The site now contains:

- One full **latest release card** (v0.1.74 detail panel)
- One **"See every release on GitHub"** link card

That's it. v0.1.0–v0.1.73 live exclusively at
`github.com/singhpratech/notepatra/releases`.

### Why

The slim rows were the first attempt at solving "the website turns
into a 20-screen wall of past changelogs," but they still showed as
horizontal stripes between the hero and the FAQ. From the user:

> "On the website only [show the] latest, [the] rest [of] older
> [versions go] on GitHub. I see horizontal lines of older versions
> why?"

Stripped 82 lines (eight slim rows: v0.1.72 → v0.1.67) from
`docs/index.html`. Updated the internal policy memory so the rule is
durable for future releases.

### Files changed

- `docs/index.html` — 82-line deletion.

## What's NOT in this release

Deferred to **v0.1.75** so v0.1.74 stays focused on the upgrade-flow
fix:

- **Runtime font-pack downloader** — Settings → Manage Fonts… that
  fetches ~25 premium open-source fonts (JetBrains Mono, Fira Code,
  Cascadia Code, IBM Plex, Geist, Monaspace, Inter, Source Serif, …)
  to `~/.local/share/notepatra/fonts/` on demand. Binary stays lite
  (~9 MB); fonts are downloaded only when the user wants them and
  registered with `QFontDatabase` immediately (no restart). Source
  files for the feature already drafted; held back until the dialog
  is end-to-end verified on each platform.

## Compatibility

- Linux (.deb / .rpm / AppImage) — unaffected, identical build.
- macOS (DMG) — unaffected.
- Windows NSIS — unaffected.
- Windows MSI (regular) — same UpgradeCode + same User-facing
  ProductName; existing v0.1.73 installs upgrade cleanly.
- Windows MSI (local-ai) — same UpgradeCode; existing v0.1.72/v0.1.73
  installs upgrade via MajorUpgrade. The new auto-generated Component
  GUIDs only conflict with the OLD shared GUIDs at uninstall, and
  MajorUpgrade handles that transparently.

## Regression coverage

- `installers/windows.wxs` — change is localized to four lines, no
  test added (would need a Windows VM with the regular MSI
  pre-installed). Validation is via the v0.1.74 GitHub Release run +
  manual install/upgrade test on Windows by anyone hitting the bug.
