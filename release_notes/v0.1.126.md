# Notepatra v0.1.126

**v0.1.125 taught `search_project` to skip credential files. It never told `open_file` or `read_tab` — so an agent that asked for `~/.ssh/id_rsa` by name still got the whole key back.**

A deep retest of v0.1.125 confirmed all four of its Windows fixes on real hardware and then found nine more defects underneath them. All nine are fixed here. There are no new editor features; every change below is a fix to the MCP surface.

## The leak came back through a different door

v0.1.125's fix was real: `search_project`'s filesystem walk consults `PathDenylist::isSecretPath`, and the regression test for it passes. It was also the *only* place the deny-list ran.

So the leak survived in the plainest possible form — stop searching, and just ask:

```
→ open_file  {"path": ".../.ssh/id_rsa"}
← "Opened .../.ssh/id_rsa as tab 8"          isError: false
→ read_tab   {"title": "id_rsa"}
← "-----BEGIN OPENSSH PRIVATE KEY-----\n<full key body>\n-----END..."
```

Three more paths were open alongside it. `find_in_tab` returns the matching *lines* of a tab, which is a content channel with extra steps. And `search_project`'s **open-tab leg** read the file straight out of the buffer — the deny-list was guarding the disk while the same bytes sat in a tab, unguarded.

Guarding a discovery path while leaving the direct-request path open is not a guard. `open_file`, `read_tab`, `find_in_tab` and both legs of `search_project` now check the same list. `open_file` refuses *before* the tab exists, because opening a key and then declining to read it would still put it on screen and in the session's tab list.

The deny-list itself did not need changing — it already covered `id_rsa` anywhere on a path, the `.env` family, `*.pem`/`*.key`/`*.jks`/`*.pfx`/`*.p12`, Terraform state, and the SSH/GPG/AWS/Docker credential directories.

## `format_json` invented data and called it success

The MCP `format_json` tool routed to the JSON panel's auto-**fixer**. That is exactly right for the panel — a human sees the repair and can undo it. Over MCP there is nobody in that loop:

| in | out | isError |
|---|---|---|
| `[1,2` | `[1,2]` | false |
| `{oops` | `{\n  oops` | false |
| `not json at all` | `notjsonatall` | false |

The first row is the one that matters. A truncated config file comes back **syntactically valid and semantically invented**, so an assistant that formats and writes it back has fabricated data the user never had — silently, and with a success flag.

The MCP path now validates strictly first, through a new non-repairing RFC 8259 check in `rust-core`, and fails with the parse position. That is what the tool's own description has always claimed: *"Fails on invalid JSON."* The JSON panel keeps its fixer, unchanged.

## "No workspace folder is open" was reported for a query that simply missed

Whether a folder is open is not a fact about your query. But the error fired only when the open tabs happened to contain nothing:

```
→ search_project {"query": "ALPHA"}                 // present in an open tab
← 1 result
→ search_project {"query": "ZZZQQQNOMATCH0000"}     // same tabs, no match
← isError:true  "No workspace folder is open…"
```

Same tabs, same scope, two different stories about the world — and an assistant told the second one pushes the user to open a folder to fix a problem that does not exist. Zero matches is a successful search now: `{results: [], truncated: false}`, with the reduced coverage carried in a `notice` field rather than an error.

## Fields the changelog promised and the wire never carried

v0.1.125's notes said `search_project` reports `workspace_searched` and `scope`. The C++ bridge did send them. The Rust `SearchResults` struct declared only `results` and `truncated`, so serde discarded the rest before the tool result was built, and no client ever saw either field.

Two layers, one contract, and only one of them updated. Both fields now cross the boundary, along with `notice`.

## The mock server had no way to say it was a mock

Run `notepatra-mcp` without `--socket` and it answers from an in-memory demo editor. That is deliberate — any MCP client can exercise the protocol with nothing installed. But v0.1.125 said so only in `--help`, and the consumer here is a language model that never runs `--help`.

Drop the flag from a config and the assistant confidently discusses three files that do not exist, on POSIX paths, on a Windows box, and reports the editor as version 0.1.118. The failure is silent and shaped exactly like success.

Now every mock tool result carries a `[MOCK DATA]` content block naming the fix (`add --socket`), plus `_meta.mock` for code; `initialize` reports `serverInfo.mock` and instructions; and the mock reports its own real version instead of a hardcoded 0.1.118.

The marker is a **separate content block**, not a prefix on the payload. Prefixing was the obvious implementation and it corrupted every JSON-returning tool on the surface — the test suite caught it immediately.

## Tabs have a stable id

Every write verb addressed its target by `tab_index`. That index is positional: close a tab to its left and it re-points at a different document, underneath a caller that has no way to notice.

```
list_open_tabs → tab 8 is notes.md
(user closes two tabs)
insert_text {"tab_index": 8, …} → lands in a different file
```

Out-of-range was the *lucky* case — you get an error. A shifted-but-still-valid index writes silently, and the approval card is the only thing between that and a corrupted file.

`list_open_tabs` now publishes an `id` per tab that survives reordering, save-as, and its neighbours closing. Every verb that names a tab accepts `tab_id`, and it takes precedence over `tab_index`. Asking for an id that is gone says so — *"no open tab has id 7 — it was closed"* — rather than reporting a bad index the caller never supplied. `tab_index` continues to work exactly as before.

## Smaller fixes

- **`read_tab` takes `max_bytes`,** and always reports `truncated` and `total_chars`. The 5 MB ceiling was the only bound, so a 2.7 MB buffer came back whole and could fill an assistant's entire context in one call — while `search_project` (`max_results`) and `run_sql` (`max_rows`) had been negotiable all along. `truncated` used to be *omitted* on a complete read, leaving the caller to infer that absent means false.
- **`find_in_tab` accepts `title`,** which `read_tab` had always accepted and which `find_in_tab` answered with `-32602 unexpected argument`. Two hand-written resolvers that had drifted; there is one resolver now, so a selector accepted by either verb is accepted by both.
- **An invalid pagination cursor is rejected.** `tools/list` and `prompts/list` ignored a bogus `cursor` and returned the full list — indistinguishable from *"your cursor was valid, here is page 2"*, which makes a paginating client loop or double-count. This server returns everything in one page and never issues a `nextCursor`, so any cursor is invalid and now gets `-32602`.

## What the retest cleared

Worth recording, because it was probed specifically to break: JSON-RPC conformance (`-32700` on garbage with the session surviving, `-32601`, `-32600`, `-32602` across missing/mistyped/unexpected arguments), resource-URI containment, path validation, byte-identical Unicode round-trips through six verbs with and without a BOM, three concurrent servers driving one editor with zero cross-talk, graceful degradation on the Lite edition, and the full write tier with a human at the keyboard — including the 120-second auto-deny observed three times and FIFO one-at-a-time card processing confirmed at exactly 240 s for two queued writes.

## Verification

Every new test was red-state verified by **restoring the pre-fix code**, not by negating a condition — a sabotage that does not reproduce the original bug's shape makes a sound test look weak. Failure signatures matched the reported defects: the key body reaching the wire, `truncated` absent on a complete read, `find_in_tab` rejecting a title, and `list_open_tabs` publishing no id.

One gap, stated plainly: the strict-JSON validator is unit-tested in `rust-core`, but its wiring into `MainWindow`'s `formatText` host lambda is verified by inspection rather than by an automated test — that lambda is not reachable from the bridge's fake host.

Also still uncovered, carried forward from the retest: the approval card's explicit **Deny button** (deny-by-timeout is proven; deny-by-click is inferred), and the remote gateway, which remains behind a non-default Cargo feature and absent from the signed binary.
