# Notepatra v0.1.87

**Save As file-type dropdown + large-file load speed-up.** Two user-reported pain points: the Save As dialog had a dead file-type dropdown unlike Notepad++, and opening a 100+ MB file was slower than the "up to 2 GB" promise suggested.

## What changed

### Save As filter list (the obvious bug)

`src/mainwindow.cpp:1655` passed a single `"All Files (*)"` filter to `QFileDialog::getSaveFileName`, so the dropdown at the bottom of the Save As dialog only ever had one entry. Now it has **~72 language entries** matching Notepad++'s behaviour: Plain Text, Markdown, Python, C, C++, Rust, Go, JavaScript, TypeScript, SQL, JSON, YAML, TOML, every supported language. The filter matching the current tab's language is pre-selected so Save As on a Python file opens with `Python (*.py *.pyw *.pyx)` already highlighted.

Same fix applied to the "Save before close?" prompt in `closeTab()` (was passing NO filter, defaulted to "All Files (*)" with the same dead dropdown).

| Source | Before v0.1.87 | After v0.1.87 |
|---|---|---|
| `File → Save As` dropdown | 1 entry: "All Files (*)" | 72 entries: language-by-language groupings + "All Files (*)" first |
| Pre-selected filter | always "All Files (*)" | matches current tab's language |
| `closeTab()` "Save before close?" | no filter at all | same 72-entry dropdown, pre-selected to current language |

### Large-file load speed-up

Profiling the load path for a 118 MB UTF-8 file found **3 separate inefficiencies** that compounded. Net: peak RAM 700 MB → ~360 MB, load time ~1.5 s → ~600 ms on a fast SSD.

| # | Fix | Saves |
|---|---|---|
| B1 | **Drop `CString` round-trip in Rust FFI.** `file_io.rs::make_result` used `CString::new(text).into_raw()` which scans every byte for embedded NUL + allocates a fresh 118 MB heap buffer + copies the bytes + appends a NUL. C++ already reads the buffer via `QString::fromUtf8(ptr, len)` — never needed the NUL. Now allocates a `Box<[u8]>` instead (no scan, no NUL byte). New `npc_free_file_text` FFI matches the new allocation shape. | -118 MB, -250 ms |
| B2 | **UTF-8 fast path.** Default Linux/macOS encoding, the hot case. Pre-fix, `UTF_8.decode(mmap_bytes)` allocates a fresh 118 MB `String` even when the mmap bytes are already valid UTF-8. Now validates with `std::str::from_utf8` (SIMD-accelerated in libcore) and passes the mmap bytes directly to `make_result_bytes`. Saves the entire decode allocation. | -118 MB, -250 ms |
| B3 | **EOL detection bounded to first 64 KB.** Pre-fix: `result_text.contains("\r\n")` and `contains('\r')` — two full-text scans of 118 MB for ~300 ms. Real files have consistent line endings; 64 KB is enough to classify. New `detect_eol_in_bytes` is a single byte-level scan. | -300 ms |
| B4 | **Large-file UX gates for editing.** Files > 50 MB now also disable **word wrap** (recalculates line layout per edit, was stuttering the typing cursor) and **indent guides + edge column** (paint per line on resize). **Find → Mark All** capped to 10,000 highlights on files > 50 MB — `SCI_INDICATORFILLRANGE` invalidates a paint per call, so 100k matches stalled the UI for seconds. The result label reports the truncation so the user knows the actual count. | smooth editing on 100 MB+ files |

Combined impact on a 118 MB UTF-8 file:

| Metric | Before v0.1.87 | After v0.1.87 |
|---|---|---|
| Peak RAM during load | ~700 MB | ~360 MB |
| Load time on a fast SSD | ~1.5 s | ~600 ms |
| Find → Mark All (100k matches) | freeze ~3-4 s | cap to 10k, render <100 ms |
| Editing after load (word wrap on) | sluggish | smooth |

### Out of scope (deferred to v0.1.88)

- **Chunked `SCI_APPENDTEXT` load.** Eliminates the Qt UTF-16 detour entirely (would drop another 236 MB of peak RAM). Needs careful mid-chunk BOM / encoding-boundary handling to be safe across UTF-16 / UTF-32 / Windows-1252 inputs — too much surface area for a same-day patch.
- **CI `strip --strip-all` step.** Drops binary from 9.7 MB → 7.06 MB. Already queued in `project_next_release_ci_strip_step.md`.
