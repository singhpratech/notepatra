# Notepatra v0.1.96 — Windows hang hotfix + platform-conventional config dirs

**Release date:** 2026-05-24

Same-day hotfix for v0.1.95 after a Windows user reported a deterministic launch hang. The post-mortem traced it to three independent design defects, all of which now have permanent fixes.

If you hit *"Notepatra is not responding"* on Windows v0.1.95 — particularly a hang where the title bar showed a recently-opened file like `.aws\config` even when launched with no arguments — this release is the fix.

---

## The bug — what users saw

| Symptom | Root cause |
|---|---|
| App window appears but `Responding = False` immediately on launch | Update check fires on the UI thread + bundled OpenSSL 1.1 is EOL since Sept 2023 → TLS handshake stalls against GitHub's modern endpoint |
| Killing via Task Manager and relaunching produces the **same hang** | Stale `session.json` keeps reopening the same file. No safety net to detect the loop. |
| Title bar shows `C:\Users\<u>\.aws\config - Notepatra` even with no file argument | Session restore opens the file on every launch — the entry never gets dropped |
| `%APPDATA%\Notepatra` is empty, but the session file exists somewhere | Notepatra wrote to `~/.config/notepatra/` on every OS — Linux-style path on Windows. IT tooling, backup tools, GPO all look in `%APPDATA%` and can't find it |

The user's manual fix was to `Stop-Process` and `Rename-Item session.json` — fine as a one-off, terrible as a recurring workflow. v0.1.96 fixes the root causes so the issue doesn't recur.

---

## Fix 1 — Platform-conventional config dir

Pre-fix every Notepatra build wrote to `~/.config/notepatra/` on every OS. v0.1.96 introduces `Config::appConfigDir()` that returns the platform-conventional location:

| Platform | Path |
|---|---|
| Linux / BSD | `$XDG_CONFIG_HOME/notepatra` (default `~/.config/notepatra`) — **unchanged** |
| macOS | `~/Library/Application Support/Notepatra` — **new** |
| Windows | `%APPDATA%\Notepatra` (e.g. `C:\Users\<u>\AppData\Roaming\Notepatra`) — **new** |

All ~6 hard-coded `~/.config/notepatra/` references in the codebase migrated:
- `Config::configPath()` (config.json)
- `MainWindow::sessionFilePath()` (session.json)
- `MainWindow::recoveryDir()` (recovery_*.txt)
- `AiInteractionLog::dbPathInternal()` (interactions.db)
- `DbConnections::configPath()` (db-connections.json)
- The plugins directory + the crash-handler recovery folder in `main.cpp`

**Migration:** on first launch of v0.1.96 on Windows or macOS, if the new platform-conventional dir is empty AND the legacy `~/.config/notepatra/` has data, the contents are **copied** (not moved) to the new location. We don't delete the legacy data — that gives users a rollback path. Cleanup of the legacy dir lands in v0.1.97.

## Fix 2 — Crash-safe session restore

Pre-fix `MainWindow::restoreSession()` had no concept of a previous-restore failure. If session.json contained an entry that hung the restore (a file on a slow/locked drive, a file the editor couldn't load, etc.), every subsequent launch would replay the same hang on the same entry — forever.

v0.1.96 adds a marker-file pattern:

1. **Before** any restore work, write a `session.json.restoring` marker file.
2. **After** restore completes successfully, delete the marker.
3. **On next launch**, if the marker still exists, the previous restore was interrupted (kill, crash, hang). Move `session.json` aside to `session.json.failed-<timestamp>` (preserving the tab list for the user) and skip restore entirely.
4. A deferred dialog (fires 800ms after the empty editor is up — does NOT block construction) tells the user: *"Previous session didn't finish restoring. Your tab list is saved at `<path>`. Rename it back if you want to retry, but expect the same hang — open the file and remove the problematic entry first."*

The marker pattern is durable across process termination — even if the user killed Notepatra mid-restore via Task Manager, the marker stays on disk and the next launch sees it.

## Fix 3 — Update check gated on EOL OpenSSL

Pre-fix `MainWindow::checkForUpdates()` ran 3 seconds after startup. Even though the update check itself is async via `QNetworkAccessManager`, the SSL handshake initialization happens synchronously inside `nam->get()` and can stall on a broken OpenSSL stack — which is exactly what happened on Windows v0.1.95.

v0.1.96 detects the OpenSSL major version at runtime and **hard-skips** the update check if it's 1.0.x or 1.1.x:

```cpp
const QString sslVer = QSslSocket::sslLibraryVersionString();
if (sslVer.contains("1.0.") || sslVer.contains("1.1.")) {
    // EOL since 2023 — TLS handshake against modern endpoints can stall.
    // Hard-skip. User sees a "open Releases page in browser" dialog only
    // if they manually triggered the check.
    return;
}
```

OpenSSL 1.1 reached end-of-life in September 2023. OpenSSL 3.0 is LTS until September 2026, 3.2/3.3 are current. Modern Notepatra builds bundle OpenSSL 3.x; older Windows installs with the 2023-vintage 1.1 DLLs simply have their update check disabled and see a non-modal hint to download manually from notepatra.org.

**Note**: the Windows MSI for v0.1.96 still ships the same OpenSSL 1.1 DLLs from 2023. Bundling OpenSSL 3.x in the Windows build is queued for v0.1.97 — it's a CI workflow change (the `windows-build` step in `.github/workflows/build.yml`) and warrants its own validation pass. The v0.1.96 gate is what stops the hang in the meantime.

---

## What this does NOT fix yet (queued for v0.1.97)

- **Bundle OpenSSL 3.x in the Windows MSI** — requires updating the CI build workflow to fetch and bundle OpenSSL 3.x DLLs instead of 1.1. Until that lands, Windows users won't get in-app update notifications, but they also won't hang on launch.
- **Auto-delete legacy `~/.config/notepatra/` after successful migration** — v0.1.96 copies but doesn't delete. v0.1.97 will sweep the legacy dir once we've validated nobody's relying on it.

## Memory rules established

- `feedback_platform_config_dir_qstandardpaths` — never hard-code `~/.config/<app>/` on cross-platform code; always use Qt's QStandardPaths or a platform-aware helper, otherwise IT tooling on Windows can't find the user's config
- `feedback_session_restore_marker_pattern` — any auto-restore loop that opens user data MUST have a "previous run failed" marker, otherwise a bad entry loops forever across user-initiated kills
- `feedback_eol_openssl_runtime_check` — before any sync network call on launch, gate on `QSslSocket::sslLibraryVersionString()` to skip EOL stacks
