# Notepatra v0.1.80

**Two paper-cut fixes: `.txt` file icons on Windows + the Search panel
Clear button no longer locks you into an undismissable empty panel.**

## Fix 1 — `.txt` files keep the Windows Notepad icon after setting Notepatra as default

### The bug

After installing Notepatra via the MSI and setting it as the default
handler for `.txt`, the file-explorer icon for `.txt` files stayed as
the old Notepad icon. Every other extension Notepatra registers
(`.md`, `.sql`, `.json`, `.py`, etc.) flipped to the Notepatra icon
immediately. Only `.txt` was stuck.

### Root cause

Windows shell icon resolution walks `UserChoice` → `ProgID` →
`DefaultIcon`. The MSI registered our `Notepatra.Document` ProgId
correctly, but **without an explicit `DefaultIcon` registry value**.
For most extensions Windows synthesises a default from the verb
target executable. For `.txt` specifically, Windows has a special-
cased fallback to the cached `txtfile`/Notepad icon — so when our
ProgId tree was missing `DefaultIcon`, the shell silently kept
serving the leftover Notepad icon. The user "fixed" the default app
but the icon never updated because nobody told the shell where our
icon lived.

The sideloaded `installers/register-associations.bat` already wrote
the right registry value:

```
reg add "HKCU\Software\Classes\Notepatra.Document\DefaultIcon" /ve /d "\"%EXE%\",0" /f
```

but the WiX MSI installer wasn't generating an equivalent.

### The fix

`installers/windows.wxs` — added `Icon="NotepatraExe" IconIndex="0"`
to the `<ProgId>` element. WiX expands this to the missing
`HKCR\Notepatra.Document\DefaultIcon\(Default) = "...\notepatra.exe,0"`
registry value, matching the sideloaded `.bat` and killing the .txt-
specific fallback path.

```xml
<ProgId Id="$(var.ProgIdName)" Description="$(var.ProgIdDescr)"
        Icon="NotepatraExe" IconIndex="0">
  <Extension Id="txt" ContentType="text/plain">
    ...
```

After the v0.1.80 MSI installs, all registered extensions —
including `.txt` — pick up the Notepatra icon at first Explorer
refresh.

## Fix 2 — Search panel: clicking Clear made the close button vanish

### The bug

Open Project Search → run a search → click **Clear** in the results
header. The results wiped (correct) but the **✕ close button also
disappeared**, leaving an empty results panel pinned open with no way
to dismiss it. The user had to click Clear *and* close from the
toolbar, or rerun a search just to get the ✕ back.

### Root cause

`src/searchresults.cpp::clear()` was hiding **both** the Clear
button and the close button, on the v0.1.46-era assumption that
"empty panel + ✕ floating" was UI noise. That conflated two distinct
user actions:

| Action  | User's mental model                              |
|---------|--------------------------------------------------|
| Clear   | Wipe the results, but keep the panel open       |
| ✕       | Dismiss the panel entirely                      |

Hiding the ✕ inside `clear()` collapsed those two actions into one
state with no recovery path.

### The fix

`src/searchresults.cpp::clear()` — removed the line that hid
`m_closeBtn`. The Clear button still hides itself (nothing left to
clear, so it has no job), but the ✕ stays visible so the user can
dismiss the empty panel on their own terms.

```cpp
void SearchResultsPanel::clear() {
    m_tree->clear();
    m_currentSession = nullptr;
    m_sessions.clear();
    m_currentFileItem = nullptr;
    m_currentFile.clear();
    // ✕ stays visible — user dismisses the empty panel themselves
    if (m_clearBtn) m_clearBtn->setVisible(false);
    if (!m_historyPath.isEmpty()) QFile::remove(m_historyPath);
    if (m_saveTimer) m_saveTimer->stop();
}
```

## Files touched

```
installers/windows.wxs    ProgId now has Icon="NotepatraExe" IconIndex="0"
                          → HKCR\Notepatra.Document\DefaultIcon registry
                          value generated by the MSI

src/searchresults.cpp     clear() no longer hides m_closeBtn; ✕ stays
                          available so user can dismiss empty panel
```

## Out of scope

- **Re-registering the icon on existing v0.1.79 installs.** Users who
  already installed v0.1.79 and set Notepatra as the default `.txt`
  handler will see the new icon once they upgrade to the v0.1.80 MSI
  (the new MSI rewrites the `DefaultIcon` registry value during
  install). The Explorer icon cache may need a logoff / `ie4uinit
  -show` to refresh in some cases — Windows-side cache, not something
  Notepatra controls.
- **NSIS installer.** NSIS doesn't register file associations at all
  (by design — it's the no-admin sideload path). Use the MSI if you
  want the shell integration.
- **macOS / Linux file-icon registration.** Both platforms use
  desktop-entry MIME associations (Linux) or `LSItemContentTypes`
  in `Info.plist` (macOS) which were already correct and aren't
  affected by this fix.
