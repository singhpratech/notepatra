# Notepatra v0.1.78

**Encoding & file-open fixes — UTF-16 / UTF-32 BOM parity with Notepad++.**

## What changed

A user opened a SQL Server `Generate Scripts` export
(`sys_table_export.sql`) and Notepatra refused with "binary file" —
but Notepad++ opened the same file as plain text. Root cause: the
file was UTF-16 LE with a `FF FE` BOM, and Notepatra's binary-file
heuristic ran *before* BOM detection.

```
Pre-v0.1.78 flow                       Notepad++ flow (what we should do)
────────────────                       ────────────────────────────────────
1. Read first 4 KB                     1. Read first 4 KB
2. Count 0x00 bytes                    2. Check BOMs (UTF-32, UTF-16, UTF-8)
3. If > 10% null → binary, refuse   →  3. If no BOM, sniff for UTF-16 pattern
4. (BOM detection never reached)       4. Fall back to UTF-8 / Windows-1252
                                       5. Only then run binary heuristic
```

UTF-16 LE encodes every ASCII character as `<char> 0x00`, so ~50% of
the bytes are NULL — way above the 10% threshold. Every UTF-16 file
was being mis-flagged. Same trap for UTF-16 BE (NULLs in even
positions) and UTF-32 LE/BE (75% NULLs).

## The fix

`rust-core/src/file_io.rs` rebuilt:

1. **BOM detection runs first.** UTF-32 LE/BE (4-byte BOMs) checked
   before UTF-16 LE (2-byte BOM), since UTF-32 LE BOM `FF FE 00 00`
   shares its first two bytes with UTF-16 LE BOM `FF FE`.
2. **Null-byte heuristic skipped for UTF-16 / UTF-32.** Their NULL
   density is legitimate, not a binary signal.
3. **No-BOM UTF-16 sniff.** Even/odd null-column ratio detects UTF-16
   without a BOM (PowerShell `Out-File`, Java
   `-Dfile.encoding=UTF-16` output). Matches Notepad++/uchardet.
4. **UTF-32 decoder.** `encoding_rs` intentionally doesn't ship a
   UTF-32 codec (WHATWG Encoding doesn't standardize it). Notepatra
   now decodes UTF-32 LE/BE manually via `u32::from_{le,be}_bytes`
   + `char::from_u32`.
5. **BOM round-trip on save.** Pre-v0.1.78, opening a UTF-16 LE BOM
   file and saving it silently stripped the BOM (because
   `QTextCodec("UTF-16LE")` emits no BOM). The C++ save path in
   `src/editor.cpp` now prepends the right BOM for every BOM-labeled
   encoding so files round-trip byte-for-byte.

| Source                                | Before v0.1.78    | After v0.1.78  | Notepad++ today |
|---------------------------------------|-------------------|----------------|-----------------|
| `sqlcmd -o file.sql`                  | binary refuse     | opens          | opens           |
| SSMS Generate-Scripts                 | binary refuse     | opens          | opens           |
| PowerShell `Out-File`                 | binary refuse     | opens          | opens           |
| Java `-Dfile.encoding=UTF-16BE`       | binary refuse     | opens          | opens           |
| Hand-stripped UTF-16 (no BOM)         | binary refuse     | opens via sniff| opens           |
| UTF-32 LE / BE (rare but legit)       | mis-decoded       | opens          | opens           |
| UTF-16 BOM file → edit → save         | BOM stripped      | BOM preserved  | BOM preserved   |
| Real binary (PNG/exe/zip)             | binary refuse     | binary refuse  | binary refuse   |

## Encoding menu

`Encoding → Reinterpret bytes as` and `Encoding → Convert to` now
list the new BOM variants alongside the no-BOM ones so users can
pick exactly what they want at save time:

```
UTF-8                  UTF-16 LE        UTF-32 LE BOM
UTF-8 BOM              UTF-16 LE BOM    UTF-32 BE BOM
                       UTF-16 BE
                       UTF-16 BE BOM
ANSI (Windows-1252)
ISO-8859-1
```

## Out of scope

- UTF-7 (`2B 2F 76 38|39|2B|2F` BOM): extremely rare, deferred.
- Universal charset detection for legacy single-byte encodings
  beyond Windows-1252 / Shift_JIS / EUC-JP / GB18030. The current
  fallback ladder handles 99 %+ of real files; uchardet integration
  is a separate decision.
